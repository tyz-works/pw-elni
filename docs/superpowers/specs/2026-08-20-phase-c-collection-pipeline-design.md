# Phase C 収集・抽出パイプライン 設計

- 日付: 2026-08-20
- 状態: 設計確定（実装計画は未作成）
- 前提: Phase B 完了（`pw.elni.net` 公開済み、3 団体とも実データ、CI 稼働）

## 1. 目的と範囲

公式サイトから興行データを日次で取り込み、`data/` への差分を PR として出す。人間は PR を読んでマージするだけにする。

### 範囲に入るもの

- **終了した興行の結果** — 勝敗・決まり手・時間・観衆
- **今後の興行予定** — 日時・会場・発表済みの対戦カード

同じ興行を日をまたいで複数回更新する流れが前提になる（発表 → カード追加 → 結果確定）。

### 範囲に入らないもの

- 選手プロフィールの定期再取得（Phase D 以降）
- ニュースの収集・要約
- 画像
- PR の自動マージ（Phase D）

### 完了条件

1. 3 団体それぞれについて、公式ページから既存の `event` JSON を更新する差分が生成できる
2. 生成された差分が `npm run validate` を通る
3. 解決できなかった名前・食い違い・失敗した団体がレポートに列挙される
4. 1 団体が壊れても他の団体の取り込みが止まらない
5. 鍵が無い環境でも（LLM 抜きで）動く

## 2. 変わらない前提（CLAUDE.md から）

設計判断ではなく制約として扱う。

- LLM に HTML を書かせない。LLM は「非構造テキスト → スキーマ準拠 JSON」の変換のみ
- 検証は非 LLM。JSON Schema + CI で機械的に落とす
- 部分失敗を許容する。1 団体が壊れても他は止めない
- 解決できない選手名から新規 wrestler を作らない。`unresolved` として人間に上げる
- スクリプトは実行環境に依存しない。設定は環境変数、パスはリポジトリルートからの相対
- 通知は失敗してもバッチ本体を落とさない
- 原文の表現を再利用しない（転載しない）

## 3. 全体構成

```
tools/collect/
├── run.mjs                    # エントリ。CLI
├── fetch.mjs                  # Playwright ラッパ。生テキスト取得だけ
├── core/
│   ├── snapshot.mjs           # .cache/snapshots/ の読み書き
│   ├── merge.mjs              # 追記マージ + conflict 検出（純関数）
│   ├── aliases.mjs            # 名前 → wrestler slug 解決（純関数）
│   ├── llm.mjs                # フォールバック抽出
│   └── report.mjs             # レポート生成（純関数）
├── adapters/
│   ├── njpw.mjs
│   ├── stardom.mjs
│   └── ddt.mjs
└── __fixtures__/{promotion}/*.txt
```

### 段の構成

```
listTargets → fetchRaw → [snapshot] → parse → resolve → merge → validate → report
                             ↑                    ↑
                        ここで永続化      unparsed のみ llm へ
```

**fetch と parse の間にスナップショットを挟むのがこの設計の要**。取得した生テキストを `.cache/snapshots/{promotion}/{id}.txt`（gitignore）に落とし、parse 以降はそこからしか読まない。

- パーサのテストがネットワークなし・固定入力で書ける
- 公式が落ちている日でも parse 以降を再実行できる
- 「公式の HTML が変わって壊れた」のか「マージが壊れた」のかを切り分けられる

### 責務の境界

**`run.mjs` は git を触らない。** やるのは「`data/` にファイルを書く」と「`.cache/report.md` を出す」の 2 つだけ。PR 作成は GitHub Actions のワークフローの仕事。ローカルでも CI でも同じコマンドが同じ結果を出すことを保証するため。

**コアは団体を知らない。** 団体ごとの差は adapter の 3 関数だけに閉じる。

```
adapter.listTargets()      → [{ id, url, kind: 'result' | 'schedule' }]
adapter.fetchRaw(target)   → string（本文テキスト）
adapter.parse(raw)         → { event: PartialEvent, unparsed: string[] }
```

**検証器は新しく書かない。** `tools/validate.mjs` は既に `--data <dir>` を受けるので、マージ後にサブプロセスで叩く。検証の門は 1 つのままにする。

書き込みの順序は次の通り。マージ結果をまず `.cache/data-staging/`（`data/` のコピーに差分を当てたもの）へ書き、そこに `validate.mjs --data` を掛ける。**通ったときだけ `data/` に反映する。** これにより、スキーマ違反のファイルが作業ツリーに残らない。`--dry-run` は検証まで走らせて `data/` への反映だけ行わない。

### CLI

```
npm run collect -- [--promotion <slug>] [--step fetch|parse|merge] [--no-llm] [--dry-run]
```

- `--promotion` 省略時は全団体
- `--step` 省略時は全段
- `--dry-run` は検証まで走らせたうえで `data/` への反映だけ行わない

## 4. 追記マージと conflict

`merge(existing, incoming)` は純関数で `{ merged, conflicts[] }` を返す。ファイル書き込みも git も知らない。

**「空」の定義**: `null` / キーが無い / 空配列。この 3 つだけが埋めてよい状態。

| 既存 | 抽出 | 動作 |
|---|---|---|
| 空 | 値 | 埋める |
| 値 | 同じ値 | 何もしない |
| 値 | 異なる値 | **上書きしない。conflict に記録** |
| 値 | 空 | 何もしない |

### 配列の扱い

- **`matches[]`** — `order` を identity にする。既存に無い `order` は追記、ある `order` は中身をフィールド単位で上のルールに掛ける
- **`sides[]`** — 配列内の位置（index）を identity にする。`wrestlerIds` が食い違えば conflict（対戦相手の変更なので人間が見るべき事象）。陣営の数そのものが違う場合も conflict にし、既存の `sides` を据え置く
- **`sources[]`** — URL で重複排除して追記。同じ URL が既にあれば `retrievedAt` は既存のまま（毎日走らせるたびに全 event の差分が出るのを避ける）

**公式からカードが消えても既存の試合は消さない。** 試合中止はあるが、消すか残すかは人間の判断。レポートに「公式側から消えた `order`」として出すだけにする。

### 唯一の特別扱い: `confirmed` の `false → true`

表の「値 → 異なる値」に当たって conflict になってしまうが、未発表 → 発表済みは日次運用でいちばん起きる遷移。**「情報が確定する方向にだけ進む」単調な遷移として許可**する。逆の `true → false` は conflict にする。

特別扱いはこれ 1 つに限定し、増やさない。

### conflict の形と扱い

```js
{ file, path: 'matches[3].result.decision', existing, incoming, sourceUrl }
```

**conflict があってもファイルは書く。** 追記できる分は反映し、食い違ったフィールドだけ既存値のまま据え置く。そのうえでレポートの先頭に列挙する。止めないのは、conflict の大半が公式側の追記・訂正で、止めると他の団体まで巻き添えになるため。

この設計により、**前の PR で人間が手で直した内容は翌日の実行で消えない**ことが保証される。

### unresolved との優先順位

同じ興行に conflict と unresolved が同時に出た場合、**unresolved が勝ちその興行は書かない**（§5）。書けない以上 conflict も反映されないが、レポートには両方を出す。人間が wrestler を足して再実行すれば、次は conflict だけが残る。

## 5. alias 解決と unresolved

`core/aliases.mjs` は純関数を 2 つ持つ。`normalize(name)` と `resolve(name, index)`。

索引は `data/wrestlers/*.json` の `name` と `aliases[]` から起動時に作る。

### normalize がやること

実際に遭遇した揺れだけを対象にする。

- NFKC 正規化（全角英数 → 半角、合字）
- 中黒とスペースの除去 — `ヤス・ウラノ` = `ヤスウラノ`、`正田 壮史` = `正田壮史`
- 英字の小文字化 — `KONOSUKE TAKESHITA` = `Konosuke Takeshita`
- 異体字の最小対応表 — `髙`→`高`、`﨑`→`崎`（DDT 公式は `髙木三四郎`、記事本文は `高木` が混在する）

### 曖昧一致はしない

正規化後の完全一致のみ。編集距離で寄せると似た名前の別人に試合を付けてしまい、しかも誰も気づかない。取りこぼしは人間に上がれば直るが、誤爆は静かに嘘になる。非対称なので取りこぼす側に倒す。

### unresolved の扱い

解決できなかった名前は wrestler を新規作成せず `unresolved` に積む。

**unresolved を含む興行は、その興行ごと書かない。** 試合を 1 つだけ落とすと「全 12 試合」の表示が嘘になるし、存在しない slug を書けば CI が孤立参照で落ちる。レポートに「団体 / 興行名 / 未解決の名前 / その名前が出てきたページの URL」を出し、人間が wrestler JSON を足してから再実行すれば次はその興行が通る。他の興行・他の団体は止めない。

### 検証器への追加チェック

`tools/validate.mjs` に **`aliases` の正規化衝突チェック**を 1 つ足す。別々の選手が同じ正規化キーを持つ状態（例: 誰かの `aliases` に他人の名前を足してしまった）があると `resolve` の挙動が実装依存になる。CI で落とす。

パイプラインが正しく動くための前提条件を、非 LLM の門で守る形にする。

## 6. LLM フォールバック

### インターフェース

`core/llm.mjs` の外向きは 1 関数だけに固定する。

```js
extract(textFragment, schemaFragment) → JSON | null
```

**モデルとプロバイダの選定は Task 8 の実測後に判断する。** このインターフェースを守る限り、差し替えは `llm.mjs` の中だけで済み、`run.mjs` も adapter も変わらない。

### 契約

1. **呼ばれる条件を狭く固定する** — `adapter.parse()` が返した `unparsed[]` にだけ効かせる。ページ全体を投げない。入力は「1 試合ぶんのテキスト断片」程度
2. **出力はスキーマで縛る** — structured outputs に `match.schema.json` の断片を渡す
3. **返ってきた JSON は必ず ajv で再検証する** — structured outputs が通っても信用しない。落ちたら 1 回だけ再試行し、それでも駄目なら `unresolved` に落とす
4. **slug を作らせない** — LLM が返すのは表示名の文字列だけ。slug への変換は §5 の決定論的な `resolve` が担う。ここを任せると存在しない slug を発明するか別人に寄せる
5. **鍵が無ければ黙って無効になる** — API キー未設定または `--no-llm` のとき「何も抽出しなかった」を返す。`unparsed` はそのまま `unresolved` に流れ、パイプラインは止まらない。**LLM は精度を上げるオプションであって動作の前提ではない**
6. **使ったことを記録する** — レポートに「どの試合を LLM が埋めたか」「モデル ID」を出す。レビュー時に「ここは機械が推測した箇所だ」と分かる状態にする

### 実装メモ（着手は Task 8 の実測後に判断）

**Task 9 は無条件には作らない。** §6-5 のとおり LLM 無しでもパイプラインは完走するので、まず
Task 1〜8 を LLM 無しで組み、DDT を実際に流して `unresolved` が何件出るかを見る。手で直して
苦にならない件数なら Task 9 は実装しない。**運用対象と課金口座が 1 つずつ減る。**

必要と判断した場合の第一候補は **Gemini API 無料枠の Flash-Lite**。

- 無料枠は 2.5 世代（Flash-Lite が 15 RPM / 1,000 RPD、250K TPM、1M コンテキスト）。この用途は
  最悪でも 1 興行 12 試合ぶん = 1 日 12 リクエストなので、RPD は 80 倍以上の余裕がある
- Gemini API の deprecations は `gemini-2.5-flash-lite` を「shutdown date 未発表」としており、
  確定時は 6 か月前告知。後継は `gemini-3.1-flash-lite`。**Vertex AI は退役日が別（2026-10-20）な
  ので使わない。** 無料枠を使うのは Gemini API / AI Studio 側
- 無料枠は送信内容が Google の製品改善・機械学習に使われ、人間のレビュアーが注釈を付けうる。
  渡すのは §6-1 のとおり公式サイトに公開済みの試合テキスト断片だけなので許容する。
  **選手プロフィール（本名・生年月日）は LLM に渡さない。** この前提が崩れるなら有料枠に移す
- 構造化出力は JSON Schema 対応。JS SDK は `@google/genai`

軽いモデルを第一候補に置けるのは **§6-4 が LLM に slug を作らせない**ため。返るのは表示名の文字列
だけで、slug 化は §5 の「正規化後の完全一致のみ」が担う。そのため取り違えの大半は既存 alias の
どれにも一致せず `unresolved` に落ちる。**弱いモデルの誤りが「静かな嘘」ではなく「取りこぼし」と
して出る構造**になっている。危険なのは「別の実在選手の alias に完全一致してしまう」場合だけで、
これは実測で見る。

誤爆が実測で問題になったときの次の候補は Claude API（`@anthropic-ai/sdk`）。確認済みの事実:

- 構造化出力は `output_config.format`（`output_format` は非推奨）
- `temperature` は Opus 5 系では廃止されており、送ると 400。**再現性はサンプリング設定ではなく
  §6-3 の再検証で担保する**
- 思考の深さは `output_config.effort`。Opus 5 は thinking が既定で on（adaptive）なので
  `thinking` は省略してよい
- 有料のみ。1 回あたり概算で入力 ~1.5K / 出力 ~350 トークン、Opus 5 で約 $0.016/回

どちらを選ぶにせよ **モデル ID は環境変数 `PW_LLM_MODEL` に既定値付きで持たせる。** §6-6 でレポート
にモデル ID を出すので、差し替えた日がレポート側に残る。

依存は選んだ SDK 1 つを `devDependencies` に足すだけ。サイトのビルドには要らない。

**LLM の課金額・呼び出し回数はパーサの出来の指標でもある。** 請求や件数が膨らんだらモデルの問題
ではなく `adapters/*.mjs` の `parse()` が壊れたサインとして読む。§8 のレポートに件数を出す。

## 7. 実行とテスト

### 取りに行く範囲

- 結果 — 直近 N 日ぶん
- 予定 — 公式のスケジュール一覧に出ている全部

マージが追記のみで冪等なので、毎日同じ興行を取り直しても 2 回目以降は差分ゼロで no-op になる。**前回どこまで取ったかの状態を持たなくて済む**のが、追記マージを選んだ副次的な利点。

### 実行環境

- **ローカル** — `npm run collect -- --promotion ddt --step parse` のように団体と段を絞って回す
- **CI** — `.github/workflows/collect.yml` を別に立てる。Phase C の開発中は `workflow_dispatch` だけにしておき、cron は最後に足す（GH Actions 上で試行錯誤する時間を避ける）。PR 作成はこのワークフローの仕事

### テスト

既存と同じ `node --test` で `tools/collect/` に置く。

- `merge.test.mjs` — 追記 / 同値 / conflict / `confirmed` の両方向 / `order` 単位のマッチ / 公式から消えた `order` を残すこと
- `aliases.test.mjs` — `normalize` の揺れと正規化キーの衝突検出
- `adapters/{promotion}.test.mjs` — フィクスチャ → `parse` → 期待 JSON

`package.json` の `test` を `node --test tools/` に広げる。これで CI の既存の「検証器そのもののテスト」ステップに collect のテストが自動的に乗り、ワークフローの追記は要らない。

### フィクスチャ

**公式ページの原文は置かない。** 構造（見出しの並び、WIN/LOSE の位置、決まり手の書式）だけ真似た架空の興行テキストを手で書いて `tools/collect/__fixtures__/{promotion}/*.txt` に置く。

- 転載にならない（リポジトリは public）
- `data/` の外なので `validate.mjs` は見ない。架空データが本番データに混ざる経路がない

### その他

`.gitignore` に `.cache/` を足す。

## 8. レポート

`run.mjs` が `.cache/report.md` に出す。GitHub Actions がこれを PR 本文に流し込む。日次の PR は 1 本で、全団体ぶんをここに載せる。

載せる 4 種類:

1. **取り込んだ変更** — 団体 / 興行 / 追記したフィールドの要約
2. **conflict** — `file` / `path` / 既存値 / 抽出値 / 出典 URL
3. **unresolved** — 団体 / 興行名 / 未解決の名前 / 出典 URL
4. **失敗した団体** — 団体 / どの段で / エラー

conflict と unresolved を先頭に置く。差分が無ければ PR を立てない。

## 9. 検討したが採らなかった案

### 常に全体を再生成して上書き

冪等で実装が最も単純だが、人間が PR で直した誤抽出が翌日の実行で差し戻される。日次で回す前提とは噛み合わない。

### フィールド単位のロック

`locked: ["matches[3].notes"]` のような保護リストを JSON に持たせる案。細かく制御できるが、スキーマと検証器の複雑さが上がる。「追記のみ・既存値は上書きしない」で同じ目的が達成でき、そちらは新しい概念を持ち込まない。

### 生データをリポジトリにコミットする

スナップショットを `data/raw/` に commit すれば、公式が消しても再現でき、diff で公式側の変更が見える。しかし**公式記事の原文をそのまま置くことになり、「原文の表現を再利用しない。転載は明確にアウト」に正面から抵触する**。リポジトリは public なので特に採らない。

### 単一パスの薄いスクリプト

1 本で fetch → parse → merge → PR まで通す案。ファイルが少なく最初は読みやすいが、テストが実質ネットワーク依存になり、壊れたときの切り分けができない。「壊れたら止まる」を優先する方針と噛み合わない。

### LLM に一律で投げる / LLM を使わない

前者は団体追加が楽で HTML 変更に強いが、コストと非決定性を常時抱える。後者は再現性が完全だが、パーサが落ちた分がそのまま欠落する。**決定論的パーサを主、LLM をフォールバック**にすることで、鍵が無い環境でも動きつつ死角を減らす。

## 10. 保留事項

- **LLM を実装するか、するならどのモデルか** — §6 のとおり Task 8 の実測（`unresolved` の件数）で決める。第一候補は Gemini API 無料枠の Flash-Lite。差し替えは `llm.mjs` 1 ファイル + `PW_LLM_MODEL`
- **`--since` の既定値（直近 N 日の N）** — Task 6 で DDT を実際に叩き、更新頻度を実測してから決める
- **cron の時刻** — Phase C の最後に決める。GH Actions の cron は数分〜十数分遅れる前提
- **通知（ntfy）** — 今回は PR 1 本に集約する方針にしたので入れない。運用してみて見落とすようなら足す
